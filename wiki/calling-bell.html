Calling Bell & Talking Clock — Start With One Unit

This page explains the whole box in plain language first, then walks through building and proving one physical unit. For that first unit, initial cost is deliberately uncapped: use a breadboard and breakout carriers so the circuit can be tested end to end. Only after the one-unit acceptance test passes does the design move to the 2-layer, ~50 × 50 mm LionCircuits PCBA with a ~₹540 ex-GST target at five units. The device is always-on and 220 V AC mains powered, strictly local-only, with a battery-backed PCF8563 RTC, a 433 MHz EV1527 trigger, and a DAC-free audio path into a PAM8403.

Reading Order

Read the Bird's Eye View first, including how the two basic functions work, then work the steps in order: 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8. Each step has a gate; do not move ahead of a failed gate. This is a separate product document, not a new section of the Apartment Thread blueprint. The circuit and part choices are locked: no alternative MCU, RTC, external DAC, or switch technology is proposed.

Bird's Eye View — What This Box Actually Does

Imagine a plastic box near the door. Someone presses a small remote outside; the box plays a chime. Every hour it also speaks the time. You set the time and upload chimes from your phone's browser — no internet account, no cloud, no router time server. If the power cuts, the clock keeps running on a coin cell inside.

The physical parts, at breadboard level

Yes — the breadboard applies to this design, but only for Step 3's single test unit. The production board in Step 8 is a printed PCB. Three Beginner Traps in This Circuit

1. Two supply voltages. The amp uses 5 V; the brain, clock chip, and receiver use 3.3 V. Feeding 5 V into a 3.3 V pin destroys parts. 2. GPIO3 has two jobs. It is the audio output in use, but also the serial input while flashing — do not let the amplifier drive it during programming. 3. The speaker wires are not ground. PAM8403 uses a bridged (BTL) output: connect the speaker between OUT+ and OUT−, never from either output to GND.

How the Two Basic Functions Are Achieved

The hardware has only two jobs: play a chime you choose, and speak the time each hour except while you are asleep. Both jobs use the same audio path — a file in flash, GPIO3, the RC filter, the amplifier, and the speaker. The difference is only what tells the brain to start playing.

1. Play any custom sound as the calling bell

   YOUR PHONE                      ESP-12F                    ________
   [web page] -- upload bytes --> [web server] -- write --> | LittleFS |
                                                            | bell file |
   OUTDOOR BUTTON                  ESP-12F                    ‾‾‾‾‾‾‾‾
   [EV1527 code] --> GPIO14 --> [match learned ID] -- read --┘
                                      │
                                      ▼
                        GPIO3 1-bit audio --> 1kΩ + 0.1µF --> PAM8403 --> SPEAKER
  1. Prepare the sound. Run the converter from Step 6 on your source audio so it becomes the exact format the firmware streams: 8 kHz, 8-bit, mono. The brain can then play it by reading bytes — there is no music decoder chip.
  2. Upload it. Join the device's local Wi-Fi, open the page the brain serves from its own flash, pick the file, and upload. The web server on the ESP-12F writes the incoming bytes into a LittleFS file named for the bell. The same page can delete or replace it.
  3. It stays there. LittleFS lives in the ESP-12F's 4 MB flash, so your chime survives power cuts. Roughly 3 MB is free for chimes because the spoken-clock pieces use only about 200 KB.
  4. Press the button. The 433 MHz receiver hears the EV1527 code and puts it on GPIO14. The firmware compares the 24-bit ID with the one you paired in the web page. On a match, it detaches that interrupt so stray radio noise cannot disturb playback.
  5. Play it. The firmware reads the stored file and emits its bits as a 1-bit Delta-Sigma stream on GPIO3. The 1 kΩ + 0.1 µF RC filter smooths that stream into an analog waveform; the PAM8403 amplifies it; the speaker connected across OUT+/OUT− makes the sound.
  6. Finish cleanly. While audio plays, the web server is paused so page requests cannot stutter the sound. When playback ends, the GPIO14 interrupt is re-attached and normal operation resumes. The next press replays the same stored file until you upload a different one.

2. Speak the clock every hour, with a bedtime

   [CR2032-backed PCF8563 clock] --I2C--> ESP-12F
                                             │
                     every minute: is it HH:00 and NOT in quiet hours?
                            ┌────────────────┴────────────────┐
                          YES                                NO
                            ▼                                ▼
   [spoken-time pieces in LittleFS] --> GPIO3 --> RC --> AMP --> SPEAKER     stay silent
  1. Set the time once. In the web page you tap a button; the phone browser sends its current date and time, and the firmware writes them into the PCF8563 over I2C (GPIO4/5). After that, the phone is no longer needed — there is no internet time server.
  2. Keep the time through power cuts. The PCF8563 runs on the CR2032 coin cell through the two Schottky diodes whenever mains power is absent, so the hour is still correct after a long outage or a reboot.
  3. Check the time every minute. The firmware reads the RTC in its main loop. When the clock reaches the top of an hour (HH:00), it prepares an announcement.
  4. Apply the bedtime rule. In the same web page you set a quiet-hours window, for example 22:00 to 06:00. The firmware compares the RTC time with that window before speaking. Inside the window it stays silent; outside it announces the hour. The check handles a window that crosses midnight.
  5. Speak the hour. Short recorded pieces (for example "the time is", the hour number, "o'clock") are stored in LittleFS at 8 kHz 8-bit mono, about 200 KB in total. The firmware stitches the right pieces together and sends them down the same GPIO3 → RC filter → PAM8403 → speaker path used by the chime. The watchdog protects the always-on loop so an hour is never missed because the firmware hung.
Key Difference From the Earlier Approach

The phone is only a one-time setup tool, not a time source that must stay online. Timekeeping lives in the coin-cell-backed chip on the board; the quiet-hours decision is made locally by the firmware from that chip's time. Custom chimes and spoken-time pieces are plain files in flash, so changing a sound never requires rewiring or reflashing.

Step 2 — Lock the Schematic & Verify Passives

Produce the complete pin-by-pin netlist first: power rails and decoupling, PAM8403 application circuit, PCF8563 crystal load caps, the GPIO3 RC filter, and the ESP-12F boot strapping. Fix these values on paper before wiring the parts from Step 1.

Locked Stack & Electrical Hazards — Read Before Any Work

Locked parts: ESP-12F (ESP8266, 4 MB flash), PCF8563 RTC + 32.768 kHz crystal + CR2032, PAM8403 Class-D amp with a DAC-free 1-bit Delta-Sigma audio path, RXB12/RXB6 433.92 MHz receiver, AMS1117-3.3 LDO, and a bare 5 V 1 A isolated SMPS. Mains: 220 V AC is present on the SMPS board — maintain HV/LV creepage and clearance with isolation slots, and let an electrician handle all mains wiring. PAM8403: its BTL outputs must never be tied together or to ground; the 4 Ω speaker connects only between OUT+ and OUT−. GPIO3: it is the ESP-12F UART RX pin during flashing and is also the audio data output — keep the audio path disconnected/muted during the one-time factory USB-UART flash and use OTA for all later updates.

Step 2 Gate — Power Budget Signed Off

PAM8403 delivers about 3 W into 4 Ω from the 5 V rail, so the amp is powered directly from the isolated SMPS. The ESP-12F generates audio with a 1-bit Delta-Sigma stream on GPIO3; a single 1 kΩ/0.1 µF RC network reconstructs it for the amp input, which removes the cost of an external I2S DAC. The AMS1117-3.3 drops 5 V to 3.3 V for the ESP-12F, PCF8563, and RXB12. Confirm bulk capacitance on the 5 V rail so an ESP8266 Wi-Fi TX burst does not sag the amp supply. Move to Step 3 only when the netlist, decoupling, strapping, and filter values are fixed.

Step 4 Gate — First Power

Only after all twelve rows pass, perform the one-time factory USB-UART flash through the 4-pin header (audio path disconnected), then reconnect the speaker and test a single quiet chime. The hardware is now ready for the firmware in Step 5.

Step 5 — Core Firmware MVP

Lean C/C++ on the Arduino ESP8266 core or ESP8266 RTOS SDK, with a LittleFS partition on the 4 MB flash. Deliver complete, untruncated code covering:

  • PCF8563 timekeeping over I2C on GPIO4/5 — set, read, and maintain date/time locally.
  • EV1527 433 MHz decoding from the GPIO14 hardware interrupt — learn and match the 24-bit transmitter ID.
  • 1-bit Delta-Sigma LittleFS audio playback on GPIO3 — the RC filter feeds the PAM8403.
  • Real-time stability — detach the GPIO14 interrupt during playback and re-attach immediately after, pause/defer HTTP handling while audio plays, and use the watchdog for 24/7 uptime.
Step 5 Gate

Flag the GPIO3 boot/flashing conflict explicitly in the firmware notes: no audio drive during the factory UART flash, OTA only afterwards. Move on only when a chime plays cleanly while the GPIO14 interrupt and web traffic are active.

Step 6 — Local Web Portal & Audio Pipeline

Serve a lightweight Vanilla HTML/JS portal directly from LittleFS with no external CDN links. It must let the user:

  • Set/sync the RTC date and time from the phone browser clock.
  • Upload and delete custom calling-bell audio files.
  • Pair/learn a 433 MHz EV1527 24-bit transmitter button ID.
  • Configure hourly/scheduled talking-clock announcements and quiet hours.
  • Trigger local OTA firmware updates.

Deliver a batch conversion command that produces talking-clock clips at 8 kHz 8-bit mono (about 200 KB total), preserving roughly 3 MB of flash for custom chimes and UI assets. Keep the portal deferred during audio playback as required in Step 5.
